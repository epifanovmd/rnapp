# Clean Code Guide

Краткие правила для ежедневной разработки. Оформление кода описано в [CONVENTIONS.md](CONVENTIONS.md), размещение по FSD — в [FSD-CHEATSHEET.md](FSD-CHEATSHEET.md), SOLID и паттерны — в [DESIGN-PRINCIPLES.md](DESIGN-PRINCIPLES.md).

## Приоритеты

Хороший код:

1. корректно решает текущую задачу;
2. читается без устного объяснения;
3. безопасно изменяется;
4. не содержит сложности без причины.

Принципы — инструменты, а не цель. Сначала простое корректное решение, затем оправданная абстракция.

## Порядок работы

1. Сформулировать требуемое поведение.
2. Определить владельца данных и side effects.
3. Написать простейшее решение.
4. Дать предметные имена.
5. Отделить вычисления от I/O.
6. Убрать подтверждённое дублирование.
7. Проверить тестами, typecheck и lint.

## KISS

Выбирай решение с минимальной когнитивной нагрузкой:

- ранний `return` вместо глубокой вложенности;
- обычную функцию вместо класса без состояния;
- явную последовательность вместо скрытой магии;
- несколько понятных условий вместо универсального rule engine;
- локальное решение вместо преждевременного framework.

Простота — не минимальное количество строк. Иногда две именованные переменные понятнее одного сложного выражения.

## YAGNI

Не реализуй возможность без текущего требования или существующей точки расширения.

Не создавать заранее:

- generic API для одного сценария;
- base class без наследников;
- plugin system без плагинов;
- десятки неиспользуемых options;
- repository поверх одного простого вызова;
- flags для несуществующих вариантов.

Удалить ненужный код лучше, чем хранить его «на будущее».

## DRY

DRY относится к знанию, а не к одинаковой форме кода.

Выносить общее, когда:

- повторяется одно бизнес-правило;
- исправление требует синхронно менять несколько мест;
- копии обязаны вести себя одинаково.

Не объединять, когда:

- сходство случайно;
- сценарии развиваются независимо;
- общая функция получает много flags;
- невозможно дать абстракции предметное имя.

Небольшое повторение безопаснее неправильной абстракции.

## Имена

Имя выражает смысл в предметной области:

```ts
// Плохо
const data = getData();
const manager = new NotificationManager();

// Лучше
const unreadMessages = getUnreadMessages();
const notificationService = new NotificationService();
```

- функция — глагол;
- boolean — вопрос: `isLoading`, `canEdit`, `hasAccess`;
- коллекция — множественное число;
- имя не повторяет уже очевидный контекст;
- избегай `manager`, `helper`, `common`, если нельзя уточнить ответственность.

## Функции

Функция должна:

- выполнять одну связную операцию;
- работать на одном уровне абстракции;
- получать зависимости явно;
- возвращать предсказуемый тип;
- не менять входные данные без контракта;
- не скрывать I/O под именем вычисления.

Чистая функция предпочтительна, когда задача является вычислением.

Много boolean-параметров скрывает смысл:

```ts
// Плохо
send(message, true, false);

// Лучше
send(message, { silent: true, retry: false });
```

Если options выбирают разные алгоритмы, используй отдельные функции или Strategy.

## React

Компонент отвечает за отображение и wiring, а не за всю бизнес-операцию.

Выноси hook, когда логика:

- использует React lifecycle/state;
- повторяется;
- имеет отдельное предметное имя;
- мешает читать основной render.

Не выноси hook только ради уменьшения файла.

Хорошая граница:

```text
Page          — координация экрана
Feature hook  — пользовательский сценарий
Entity store  — состояние сущности
Service       — инфраструктурный side effect
UI component  — отображение
```

Derived state вычисляется из источника. Не синхронизируй его отдельным effect без необходимости.

## Side effects

У side effect должен быть явный владелец lifecycle:

- HTTP/socket/storage скрыты за понятным API;
- subscription возвращает cleanup;
- timer очищается;
- конкурентный запрос учитывает cancellation или stale result;
- глобальный provider монтируется в composition root;
- повторная инициализация безопасна либо запрещена контрактом.

Не запускай I/O внутри utility, имя которой обещает только вычисление.

## Ошибки

Ошибка обрабатывается один раз на подходящем уровне:

- инфраструктура добавляет технический контекст;
- сценарий решает, можно ли восстановиться;
- UI показывает понятное состояние;
- глобальный interceptor не дублирует сообщение feature.

Не превращай ошибку в `null`, если `null` означает отсутствие данных. Ожидаемую ошибку удобно представлять явным Result-контрактом.

## Когда рефакторить

Сигналы:

- одно изменение требует правок в нескольких несвязанных местах;
- невозможно дать функции короткое имя;
- модуль меняется по разным причинам;
- растёт число flags и ветвлений;
- тест требует слишком много инфраструктуры;
- наружу постоянно импортируют внутренние детали;
- поведение опасно менять из-за скрытых side effects.

Сначала зафиксируй поведение тестом. Меняй структуру небольшими шагами и не смешивай рефакторинг с новым поведением без необходимости.

## Checklist

- [ ] Основной сценарий читается сверху вниз.
- [ ] Имена выражают предметный смысл.
- [ ] Нет возможностей без требования.
- [ ] У модулей понятна ответственность.
- [ ] Дублируется знание, а не просто похожие строки.
- [ ] Side effects видимы и очищаются.
- [ ] Ошибка обрабатывается на одном уровне.
- [ ] Абстракция упрощает основной сценарий.
- [ ] Поведение покрыто соразмерной проверкой.
