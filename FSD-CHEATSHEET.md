# FSD: архитектурная шпаргалка

Краткое руководство для ежедневных решений. Полное описание конкретного проекта — в [ARCHITECTURE.md](ARCHITECTURE.md). Базовые термины соответствуют [официальной документации Feature-Sliced Design](https://feature-sliced.design/docs/reference/slices-segments).

## 1. Иерархия

```text
app → pages → widgets → features → entities → shared
```

Импортировать можно только вниз. Слайсы одного слоя независимы и напрямую друг друга не импортируют.

| Слой       | Что здесь находится                                                        | Контрольный вопрос                             |
| ---------- | -------------------------------------------------------------------------- | ---------------------------------------------- |
| `app`      | запуск приложения, router/navigation, глобальные providers, DI composition | Без этого приложение как система запустится?   |
| `pages`    | целые экраны для router/navigation                                         | Это можно напрямую зарегистрировать как экран? |
| `widgets`  | крупные самостоятельные блоки страницы                                     | Это законченный блок, используемый на экранах? |
| `features` | пользовательские действия и сценарии                                       | Пользователь делает это с сущностью?           |
| `entities` | бизнес-понятия, их состояние и представление                               | Это существительное предметной области?        |
| `shared`   | переиспользуемый фундамент без бизнес-смысла                               | Это пригодилось бы в другом приложении?        |

## 2. Слайсы и сегменты

У `pages`, `widgets`, `features` и `entities` второй уровень — слайс:

```text
features/
  sign-in/       ← слайс
  edit-profile/  ← слайс
```

Внутри слайса код группируется по назначению:

| Сегмент  | Содержимое                                               |
| -------- | -------------------------------------------------------- |
| `ui`     | компоненты, относящиеся к отображению форматтеры и стили |
| `model`  | состояние, схемы, бизнес- и сценарная логика             |
| `api`    | запросы, DTO, мапперы и API-адаптеры                     |
| `lib`    | вспомогательный код, нужный только этому слайсу          |
| `config` | конфигурация и feature flags                             |

Не нужно создавать пустые сегменты. Маленький слайс может оставаться плоским:

```text
features/sign-out/
  index.ts
  SignOutButton.tsx
  useSignOut.ts
```

Когда файлов становится больше или появляются разные назначения, структура раскрывается:

```text
features/sign-out/
  index.ts
  ui/
    SignOutButton.tsx
  model/
    useSignOut.ts
```

`pages` подчиняется тем же правилам. Страница может иметь `ui`, `model`, `api` и `lib`. Группы маршрутов или навигаторов (`stack`, `tabs`, `_auth`) — это группы слайсов, а не сегменты; общий код в них класть нельзя.

У `app` и `shared` слайсов нет. Их директории верхнего уровня — сегменты или самостоятельные тематические модули.

## 3. Как называть сегменты

Имя должно описывать назначение, а не вид файла.

Правильно:

```text
ui/
model/
api/
lib/
config/
validation/
navigation/
notifications/
```

Не использовать для новых сегментов:

```text
components/
hooks/
types/
utils/
```

Причина: такие имена сообщают, чем является файл, но не зачем он существует. Тип, хук или компонент следует хранить рядом с кодом того же назначения.

Дополнительный сегмент допустим, если у него есть ясная предметная роль и граница ответственности. Существующие legacy-папки с техническими именами не являются образцом для нового кода.

## 4. Public API

Каждый слайс предоставляет один корневой `index.ts`:

```text
entities/user/
  index.ts       ← внешний API
  model/store.ts ← внутренняя реализация
  ui/Avatar.tsx  ← внутренняя реализация
```

Снаружи:

```ts
import { IUserStore, Avatar } from "@entities/user";
```

Нельзя:

```ts
import { IUserStore } from "@entities/user/model/store";
```

Внутри своего слайса используются относительные пути:

```ts
import { IUserStore } from "../model/types";
```

Не следует экспортировать «на всякий случай». Public API содержит только то, что действительно разрешено использовать внешним потребителям.

В `shared` public API определяется на уровне самостоятельного модуля:

```text
shared/ui/button/index.ts
shared/lib/notifications/index.ts
shared/lib/socket/index.ts
```

## 5. Направление зависимостей

| Откуда     | Разрешено импортировать                     |
| ---------- | ------------------------------------------- |
| `shared`   | `shared`                                    |
| `entities` | `shared`                                    |
| `features` | `entities`, `shared`                        |
| `widgets`  | `features`, `entities`, `shared`            |
| `pages`    | `widgets`, `features`, `entities`, `shared` |
| `app`      | все слои                                    |

Сегменты внутри одного слайса не являются мини-слоями. FSD не задаёт обязательного порядка `ui → model → api`. Если проект вводит такой порядок, это отдельное локальное правило.

Если слайсам одного слоя нужен общий код:

1. Проверить, действительно ли это одна ответственность и не нужно ли объединить слайсы.
2. Если код общий и бизнесовый — опустить его в подходящий нижний слой.
3. Если нижнему слою нужны данные верхнего — применить Dependency Inversion: контракт хранится внизу, реализация — наверху.
4. Для неизбежных связей между entities использовать явный cross-public API `@x`, а не скрытый deep import.

## 6. Куда положить новый код

### Новый компонент

- Базовый переиспользуемый UI без бизнес-смысла → `shared/ui`.
- Представление сущности → `entities/<entity>/ui`.
- Часть пользовательского действия → `features/<feature>/ui`.
- Крупный законченный блок → `widgets/<widget>/ui`.
- Разметка конкретного экрана → `pages/<page>/ui`.
- Глобальный provider/host, собирающий приложение → `app`.

### Новая логика

- Состояние и правила сущности → `entities/<entity>/model`.
- Сценарий действия пользователя → `features/<feature>/model`.
- Состояние только конкретной страницы → `pages/<page>/model`.
- Универсальный технический механизм → тематический модуль в `shared/lib`.
- Инициализация и связывание модулей → `app`.

### Новый API-вызов

- Универсальный HTTP-клиент и сгенерированные контракты → `shared/api`.
- Запрос, принадлежащий сущности → `entities/<entity>/api`.
- Запрос, существующий только ради одного пользовательского сценария → `features/<feature>/api`.
- Не класть сетевой вызов в `ui`.

## 7. Feature или widget

`feature` — действие:

- войти;
- выйти;
- изменить профиль;
- восстановить пароль;
- отсканировать контейнер.

`widget` — законченный блок композиции:

- форма/панель чата вместе с данными и действиями;
- header приложения;
- крупная карточка профиля с несколькими features;
- навигационная панель.

Компонент не становится widget только из-за размера файла. Если он остаётся частью одного действия, это `feature/ui`.

## 8. Page

Page:

- соответствует маршруту или экрану навигатора;
- собирает нижние слои;
- содержит только специфичную для экрана координацию;
- не становится хранилищем переиспользуемой бизнес-логики.

Если часть страницы нужна на нескольких экранах, определить её природу и перенести в `widget`, `feature` или `entity`.

## 9. Providers и notifications

Расположение зависит от ответственности:

- универсальный контракт и сервис уведомлений → `shared/lib/notifications`;
- переиспользуемое визуальное представление toast → `shared/ui/notifications` либо публичная UI-часть тематического shared-модуля;
- глобальный provider/host, который только подключает библиотеку к конкретному приложению → `app/providers/notifications`.

Provider допустимо оставить рядом с shared-модулем, только если он является частью его переносимого публичного API и не знает о конфигурации приложения.

## 10. Связанные конвенции

Правила именования файлов, одного компонента на файл, TypeScript, hooks, imports,
комментариев и тестов находятся в [CONVENTIONS.md](CONVENTIONS.md). Эта шпаргалка отвечает
только за выбор архитектурного места.

## 11. Чек-лист перед merge

- [ ] Код находится на минимально подходящем слое.
- [ ] Название слайса описывает предметную область или пользовательское действие.
- [ ] Сегменты описывают назначение, а не тип файлов.
- [ ] Нет импортов вверх и между соседними слайсами.
- [ ] Внешние импорты идут через public API.
- [ ] Внутри слайса используются относительные пути.
- [ ] Public API не раскрывает лишнюю реализацию.
- [ ] Код соответствует [CONVENTIONS.md](CONVENTIONS.md).
- [ ] Выполнены lint, typecheck и тесты проекта.
