# Design Principles and Patterns

Как применять SOLID и паттерны без избыточной архитектуры. Общий подход к чистому коду — в [CLEAN-CODE.md](CLEAN-CODE.md).

## Правило выбора

Паттерн применяется только к сформулированной проблеме.

Перед внедрением спроси:

1. Какая проблема уже существует?
2. Почему функция или простой объект её не решает?
3. Станет ли основной сценарий понятнее?
4. Есть ли реальные варианты или внешняя граница?
5. Можно ли удалить паттерн без потери поведения?

Если проблема не формулируется, паттерн не нужен.

## SOLID

### S — Single Responsibility

Модуль имеет одну ответственность и одну основную причину измениться.

Нарушение: component загружает данные, валидирует форму, управляет navigation и рисует сложный UI.

Исправление: разделить сценарий, инфраструктуру и отображение. Не дробить линейную операцию на десяток одноразовых функций.

### O — Open/Closed

Стабильный код расширяется добавлением варианта, а не постоянной правкой центральной цепочки условий.

Применять Strategy/registry, когда варианты уже существуют и меняются независимо. Пока вариантов мало и они меняются вместе, обычный `if` или `switch` проще.

### L — Liskov Substitution

Каждая реализация честно соблюдает контракт:

- принимает те же допустимые входы;
- возвращает совместимый результат;
- сохраняет обещанные side effects;
- не требует скрытых условий;
- не выбрасывает неожиданные ошибки.

Если часть реализаций не поддерживает метод, интерфейс выбран неверно.

### I — Interface Segregation

Потребитель зависит только от нужной части API.

Вместо одного большого `NotificationSystem` могут существовать:

```ts
interface NotificationService {
  show(): void;
  dismiss(): void;
}

interface NotificationStore {
  subscribe(): void;
  clearQueue(): void;
}
```

Разделяй интерфейс при разных потребителях, а не ради количества файлов.

### D — Dependency Inversion

Высокоуровневая логика зависит от контракта, инфраструктура его реализует.

Применять на границах:

- storage;
- HTTP/socket;
- notifications;
- analytics;
- platform API;
- clock/randomness для тестов.

Контракт принадлежит потребителю. Не создавай интерфейс для каждого простого класса с одной реализацией.

## Композиция вместо наследования

Предпочитай:

- props и slots для UI;
- hooks и функции для поведения;
- constructor injection для services;
- Strategy callback для алгоритма.

Наследование допустимо при настоящем отношении «является» и стабильном базовом контракте. Не используй его только ради повторного использования пары методов.

## Основные паттерны

| Проблема                        | Паттерн              | Когда применять                              |
| ------------------------------- | -------------------- | -------------------------------------------- |
| Нужно скрыть API библиотеки     | Adapter              | Внешний API не должен протекать в приложение |
| Нужен простой вход в подсистему | Facade               | Несколько шагов всегда выполняются вместе    |
| Есть взаимозаменяемые алгоритмы | Strategy             | Варианты меняются независимо                 |
| Создание зависит от окружения   | Factory              | Выбор реализации не принадлежит потребителю  |
| Код не должен знать реализацию  | Dependency Injection | Есть важная внешняя граница                  |
| Потребители реагируют на state  | Observer             | Нужна подписка один-ко-многим                |
| Успех и ошибка ожидаемы         | Result               | Оба исхода являются нормальным потоком       |
| UI собирается из частей         | Composition / Slots  | Части должны заменяться независимо           |

## Практический пример: notifications

Чистое разделение:

```text
NotificationService  — публичные операции
NotificationStore    — состояние и подписки UI
Library adapter      — react-hot-toast / native host
Provider or Host     — подключение в composition root
Feature              — вызывает контракт, не знает библиотеку
```

Здесь применяются:

- SRP — отдельные причины изменения;
- ISP — service и store имеют разных потребителей;
- DIP — feature зависит от контракта;
- Adapter — детали библиотеки скрыты;
- Facade — внешний API уведомлений остаётся простым.

Не нужно добавлять Factory или Strategy, пока нет нескольких способов создания или взаимозаменяемых алгоритмов.

## Частые ошибки

- Применять паттерн ради названия.
- Создавать интерфейс для каждого класса.
- Считать любое повторение нарушением DRY.
- Добавлять абстракцию «на будущее».
- Прятать простой сценарий за generic framework.
- Использовать наследование ради нескольких общих строк.
- Создавать Strategy для единственного алгоритма.
- Делить API без разных потребителей.

## Checklist

- [ ] У паттерна есть конкретная проблема.
- [ ] Простое решение недостаточно.
- [ ] Основной сценарий стал понятнее.
- [ ] Контракт принадлежит потребителю.
- [ ] Все реализации соблюдают контракт.
- [ ] Интерфейс не заставляет потребителя зависеть от лишнего.
- [ ] Абстракция имеет реальные варианты или важную внешнюю границу.
