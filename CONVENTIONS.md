# Project Conventions

Единые обязательные соглашения для React Vite и React Native проектов. Этот документ отвечает на вопрос «как писать код».

- Архитектурные решения и текущее устройство проекта: [ARCHITECTURE.md](ARCHITECTURE.md).
- Выбор слоя, слайса и сегмента: [FSD-CHEATSHEET.md](FSD-CHEATSHEET.md).
- Чистый код, SOLID и паттерны: [CLEAN-CODE.md](CLEAN-CODE.md) и
  [DESIGN-PRINCIPLES.md](DESIGN-PRINCIPLES.md).
- Если правило расходится с автоматически проверяемой конфигурацией, фактическое поведение ESLint фиксируется в `eslint.config.mjs`, а расхождение должно быть устранено отдельно.

## 1. Область действия

Правила распространяются на ручной код в `src` или `template/src`.

Не редактируются вручную:

- сгенерированный API-код;
- route tree и другие файлы, созданные router/codegen;
- платформенные codegen-спеки React Native;
- сборочные артефакты.

Требования внешнего фреймворка или генератора имеют приоритет только для принадлежащих ему файлов. Исключение должно быть локальным и задокументированным.

## 2. Именование директорий

Папки именуются в `kebab-case`:

```text
sign-in/
edit-profile/
input-bar/
token-storage/
```

Имена слайсов описывают предметную область или пользовательское действие. Имена сегментов описывают назначение кода.

Не создавать новые сегменты с именами:

```text
components/
hooks/
types/
utils/
```

Допустимые стандартные сегменты: `ui`, `model`, `api`, `lib`, `config`. Дополнительное имя допустимо, если выражает устойчивую ответственность модуля.

Route groups, navigator groups и служебные каталоги фреймворка могут использовать требуемое фреймворком имя.

## 3. Именование файлов

| Содержимое                      | Соглашение                            | Пример                                 |
| ------------------------------- | ------------------------------------- | -------------------------------------- |
| React-компонент                 | `PascalCase.tsx`                      | `SignInForm.tsx`                       |
| React-хук с основным экспортом  | имя файла совпадает с экспортом       | `useSignInVM.ts`                       |
| Shared utility hook             | принятый в модуле `use-kebab-case.ts` | `use-latest-ref.ts`                    |
| Обычный TypeScript-модуль       | `kebab-case.ts`                       | `token-storage.ts`                     |
| Store в доменном слайсе         | `store.ts`                            | `entities/user/model/store.ts`         |
| Валидация                       | `validation.ts`                       | `features/sign-in/model/validation.ts` |
| Константы одного модуля         | `constants.ts`                        | `model/constants.ts`                   |
| Типы всего небольшого сегмента  | `types.ts`                            | `model/types.ts`                       |
| Типы одного крупного компонента | `<name>.types.ts`                     | `image-viewing.types.ts`               |
| DI-регистрация                  | `<slice>.module.ts`                   | `auth.module.ts`                       |
| Public API                      | `index.ts`                            | `features/sign-in/index.ts`            |
| Dependency Inversion contract   | `<name>.contract.ts`                  | `token-source.contract.ts`             |

Имя не повторяет контекст без необходимости: внутри `entities/user/model` предпочтительно `store.ts`, а не `user-store.ts`.

Если файл `.tsx` не экспортирует компонент, его имя всё равно должно описывать основной экспорт. Не использовать JSX как причину складывать несвязанные декларации в один файл.

## 4. React-компоненты

В одном файле объявляется не более одного React-компонента.

Это относится к:

- экспортируемым компонентам;
- локальным helper-компонентам;
- компонентам внутри `memo` и `forwardRef`;
- render-компонентам compound API.

Обычные render-функции, возвращающие `ReactNode` для callback API, не становятся отдельным компонентом, если не используются через JSX и не имеют собственного React lifecycle.

Helper-компонент выносится в отдельный файл рядом с потребителем. Если он нужен только одному компоненту, экспортировать его из public API не нужно.

`memo` применяется по измеримой причине или когда стабильность компонента является частью существующего performance-контракта. Нельзя снимать мемоизацию только ради прохождения структурного правила — реализацию и обёртку следует разделить корректно.

`forwardRef)-компоненту задаётся понятный display name, если инструменты не могут вывести его автоматически.

## 5. Экспорты и public API

Корневой `index.ts` слайса формирует его внешний контракт и не содержит реализацию.

Правильно:

```ts
export { SignInForm } from "./ui/SignInForm";
export { useSignIn } from "./model/useSignIn";
export type { SignInFormValues } from "./model/types";
```

Не использовать массовый `export *`, если он случайно раскрывает внутренние детали или создаёт коллизии.

Public API экспортирует только то, что поддерживается для внешних потребителей. Внутренние компоненты, store-классы и implementation details не экспортируются «на всякий случай».

Deep import во внутреннюю структуру чужого слайса запрещён.

## 6. Импорты

- Между слоями и слайсами используются aliases.
- Внутри своего слайса или shared-модуля используются относительные пути.
- Импорт идёт через public API внешнего слайса.
- Импорты сортируются автоматически правилами `simple-import-sort`.
- Не создавать циклические зависимости через barrel-файлы.
- Type-only зависимости оформляются через `import type`, когда импорт не нужен в runtime.

Правильно:

```ts
import { IAuthStore } from "@entities/auth";
import type { SignInFormValues } from "../model/types";
```

Неправильно:

```ts
import { IAuthStore } from "@entities/auth/model/types";
import { SignInFormValues } from "@features/sign-in";
```

Второй пример является self-import, если расположен внутри `features/sign-in`.

## 7. TypeScript и типы

- Не использовать `any`, если тип можно выразить безопасно.
- Не скрывать ошибку типов через необоснованные assertion и `as unknown as`.
- Тип располагается максимально близко к месту владения.
- Общий `shared/types` или сегмент `types` не создаётся.
- DTO находится рядом с API-контрактом; доменная модель — в `model`.
- Props компонента называются `I<Component>Props` или `<Component>Props` согласно уже принятому стилю модуля; внутри одного модуля стиль не смешивается.
- Публичные типы экспортируются явно через `export type`.
- Глобальные declaration augmentation используются только для действительно глобальных контрактов.

## 8. React-хуки

- Hooks вызываются только на верхнем уровне React-компонента или другого hook.
- Имя начинается с `use`.
- Dependency array отражает фактические зависимости и семантику эффекта.
- Нельзя механически менять dependency array только ради линтера, не проверив изменение поведения.
- Для стабильного callback, которому нужны свежие значения, используется принятый в проекте latest-ref/use-event паттерн.
- Mount-only effect должен быть действительно mount-only; причина стабильности зависимостей должна быть очевидна из структуры кода.
- Новые отключения `react-hooks/exhaustive-deps` не добавляются без отдельного обоснованного архитектурного решения.
- Существующие точечные suppressions не расширяются и не считаются примером для нового кода.

Custom hook возвращает минимальный контракт. Навигация, UI и инфраструктура не смешиваются с model-логикой без необходимости.

## 9. State и side effects

- Store хранит состояние и переходы, а не разметку.
- API и platform adapters находятся вне UI-компонента.
- Side effect запускается на уровне, который владеет его жизненным циклом.
- Глобальная инициализация, providers и composition находятся в `app`.
- Feature не выполняет навигацию, если результат сценария может быть сообщён callback/result и обработан page/app.
- Подписки, таймеры и listeners обязательно освобождаются.
- Асинхронный код учитывает cancellation или устаревший результат, когда это влияет на UI.

## 10. Стили и UI

### Web

- Используются принятые design tokens и UI-kit.
- Глобальные стили допустимы только в app-level styles.
- Компонент не добавляет произвольный глобальный CSS.
- Inline style допустим для действительно динамического значения; статическое оформление выносится в принятый механизм стилей.

### React Native

- Статические стили объявляются через `StyleSheet.create`.
- Динамические значения добавляются отдельным элементом массива styles.
- Не создавать новый объект статического style на каждом render.
- Platform-specific файл используется, когда реализация действительно различается, а публичный API остаётся единым.
- Native/codegen naming не изменяется вопреки требованиям React Native.

## 11. Ошибки и результаты

- Ошибки не игнорируются молча.
- Пользовательское сообщение отделяется от технической ошибки.
- 401/session-expired обрабатывается централизованно в auth/http lifecycle.
- Не показывать несколько одинаковых уведомлений из разных уровней одного запроса.
- Если проект использует result contract `{ data } | { error }`, новый код сохраняет этот контракт и не смешивает его с исключениями без отдельного решения.

## 12. Комментарии и документация

Комментарий объясняет причину, ограничение или неочевидный контракт, а не пересказывает код.

Допустимы:

- краткий JSDoc публичного контракта;
- объяснение неочевидного performance/lifecycle решения;
- требование внешней библиотеки или платформы;
- обоснование локального исключения.

Не допускаются:

- история изменений;
- закомментированный старый код;
- очевидное описание следующей строки;
- комментарий, маскирующий неверное имя или слишком сложную функцию.

При изменении архитектурного факта обновляется `ARCHITECTURE.md`. При изменении общих правил — этот документ. `FSD-CHEATSHEET.md` меняется только при изменении рекомендаций по размещению кода.

## 13. Тесты

- Тест проверяет наблюдаемое поведение, а не внутреннюю реализацию.
- Исправление дефекта сопровождается regression test, если сценарий можно стабильно воспроизвести.
- Не использовать snapshot как единственную проверку важной бизнес-логики.
- Mocks располагаются рядом с тестом или в принятой тестовой инфраструктуре.
- Тесты не зависят от порядка запуска и очищают изменённое глобальное состояние.
- Сгенерированный код напрямую не тестируется; тестируется адаптер или потребитель.

## 14. ESLint и форматирование

- ESLint не отключается для файла или директории ради прохождения проверки.
- Новое локальное отключение правила допустимо только когда правило неприменимо технически, причина указана рядом, а более узкого решения нет.
- Autofix используется только после просмотра затрагиваемых файлов.
- Форматирование не смешивается с несвязанным функциональным изменением.
- Ошибки lint и typecheck исправляются в рамках задачи.
- Новое предупреждение считается незавершённой работой.

Часть соглашений проверяется автоматически, часть — только code review. Таблица реальных автоматических проверок находится в `ARCHITECTURE.md` каждого проекта.

## 15. Исключения

Исключение должно быть:

1. вызвано требованием framework/codegen/platform или подтверждённым техническим ограничением;
2. максимально узким;
3. задокументированным рядом с настройкой или в проектном разделе `ARCHITECTURE.md`;
4. не расширяемым на новый код автоматически.

Платформенные исключения конкретного проекта перечисляются в его `ARCHITECTURE.md`.

## 16. Проверка перед merge

### React Vite

```bash
npx eslint "src/**/*{.ts,.tsx}"
npx tsc --noEmit
yarn build
```

### React Native

Из корня repository:

```bash
make check
```

Или из `template`:

```bash
yarn run check
```

Для Yarn 1 используется именно `yarn run check`: `yarn check` является встроенной командой Yarn.

Дополнительно:

```bash
git diff --check
```

## 17. Checklist

- [ ] Файл и директория названы по соглашению.
- [ ] В файле не больше одного React-компонента.
- [ ] Типы находятся рядом с владельцем.
- [ ] Нет deep import и self-import через alias.
- [ ] Public API не раскрывает лишнюю реализацию.
- [ ] Dependency arrays не изменены механически.
- [ ] Нет новых необоснованных suppressions.
- [ ] Статические стили не создаются внутри render.
- [ ] Подписки и таймеры очищаются.
- [ ] Комментарии объясняют причину, а не код.
- [ ] Документация обновлена, если изменился контракт.
- [ ] Выполнены проверки соответствующего проекта.
